SkillHub — Guía de Sustentación

Documento de preparación para la sustentación y defensa de la Prueba de Desempeño .NET — SkillHub.

1. 🎤 El Discurso Inicial (Tu presentación de 1 minuto)

"Buenas tardes. Para esta prueba de desempeño desarrollé la plataforma SkillHub, una solución integral para gestionar talleres presenciales y sus inscripciones, resolviendo problemáticas reales como el sobrecupo, duplicados, cruces de horarios y control de cancelaciones.

Implementé una arquitectura basada en Clean Architecture dividida en 4 capas desacopladas, utilizando Entity Framework Core con Code First y PostgreSQL, ASP.NET Core Identity con JWT para autorización basada en roles (Empleado y Participante), y dos capas de presentación: una REST API con Swagger y una aplicación Web MVC que consume directamente la capa de aplicación."

2. 🏛️ Cómo explicar la Arquitectura (Clean Architecture)

  1. SkillHub.Domain (El Núcleo): Contiene las entidades principales (Workshop, Enrollment, ApplicationUser), Enums y excepciones de negocio. El dominio es C# puro; no depende de Entity Framework ni de bases de datos. No es un modelo anémico: las entidades contienen sus propias reglas.
  2. SkillHub.Application (Casos de Uso): Contiene los DTOs y los servicios (WorkshopService, EnrollmentService, AuthService, ReportService). Define las abstracciones para librerías externas (IPdfReportGenerator y IExcelReader), cumpliendo el Principio de Inversión de Dependencias (DIP).
  3. SkillHub.Infrastructure (Detalles Técnicos): Implementa la persistencia con ApplicationDbContext (PostgreSQL), los Repositorios, UnitOfWork, generación de PDF con QuestPDF y lectura de Excel con EPPlus.
  4. Capas de Presentación:
    • SkillHub.Api: Expone los endpoints REST para Swagger, Postman y empleados.
    • SkillHub.Web: Aplicación MVC para participantes (Opción A). Ambas capas consumen la misma lógica de Application.

3. 🛡️ Las Reglas de Negocio en el Código

Regla Dónde está en el código Qué responder
1. Cupos Dinámicos Workshop.cs → GetAvailableCapacity() El taller calcula sus cupos restando solo las activas (Capacity - ActiveEnrollmentsCount). Las canceladas liberan el cupo.
2. Sin Duplicados EnrollmentService.cs → EnrollAsync() Consulto si el participante ya tiene una inscripción Active. Si existe, lanzo BusinessRuleException.
3. Sin Cruces de Horario Workshop.cs → OverlapsWith() Fórmula matemática: StartDateTime < other.End && EndDateTime > other.Start. Si se cruza con otro taller activo, se rechaza.
4. Solo Talleres Futuros Workshop.cs → Validate() Se valida que StartDateTime > DateTime.UtcNow tanto al crear el taller como al inscribirse.
5. Cancelación (24h) Enrollment.cs → Cancel() Participante solo puede cancelar si faltan 24h o más. Empleado puede cancelar en cualquier momento antes del inicio. Audita quién y cuándo.
6. Reinscripción EnrollmentService.cs Como la inscripción previa quedó en estado Cancelled, ya no cuenta como activa y se puede volver a inscribir.

5. ❓ Preguntas Frecuentes y Respuestas Clave

¿Por qué la lógica de cancelación está en la entidad Enrollment y no en el Controller?

"Porque en Clean Architecture aplicamos Domain-Driven Design: las reglas que gobiernan el ciclo de vida del negocio deben vivir dentro del Dominio para evitar modelos anémicos y garantizar que ninguna otra capa pueda violar la regla de las 24 horas."

¿Dónde se implementó la generación de PDFs y por qué?

"En la capa de Infrastructure usando QuestPDF, pero desacoplada detrás de la interfaz IPdfReportGenerator en Application, cumpliendo con el Principio de Inversión de Dependencias (DIP)."

¿Cómo manejas los errores para que la API no se caiga?

"Implementé un middleware personalizado GlobalExceptionHandlingMiddleware que intercepta las excepciones del dominio: captura NotFoundException (404), BusinessRuleException (400 Bad Request) y formatea un JSON estándar con mensaje claro."

¿Cómo se cargaron los datos iniciales?

"Creé un servicio DataSeeder que se ejecuta automáticamente en el arranque de la aplicación (Program.cs), verificando que los roles, instructores y talleres existan en PostgreSQL desde el primer arranque."
